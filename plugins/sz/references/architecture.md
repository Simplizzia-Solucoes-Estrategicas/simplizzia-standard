# Architecture (Next.js App Router)

Rules, then recipes, then the conformity checklist. `example/` implements every recipe with real code that passes the standard's typecheck and lint: copy its shape.

## Stack (pinned)

Next.js 16 App Router · TypeScript 5 strict · ESLint 9 · Tailwind + shadcn/ui · Supabase via @supabase/ssr · next-safe-action 8 · zod 4 behind `v` · @t3-oss/env-nextjs · react-hook-form.

Never bump a major version. typescript-eslint requires TypeScript < 6.1 and the React lint plugin requires ESLint 9, even though newer majors exist. Upgrades are the lead's call.

Next 16 is not the Next.js of older tutorials: `src/proxy.ts` instead of `middleware.ts`; `cookies()`, `headers()` and `params` are async; there is no Pages Router (`pages/`, `getServerSideProps`). When unsure, read `node_modules/next/dist/docs/` instead of relying on memory.

## Tree

```
src/
  app/                 routes only: page.tsx renders a screen, layout.tsx, api/**/route.ts
  screens/<Name>/      <Name>Screen.tsx + the parts only this screen uses (+ *.hook.ts)
  components/
    ui/                generated by shadcn/ui; nothing written by hand
    <Feature>/         components used by two or more screens
  data/<domain>/       schema.ts · queries.ts (reads, server-only) · actions.ts (Server Actions)
                       · admin.ts (admin client, webhook/cron only)
  lib/                 infrastructure: env, auth, action-client, route, validation/v,
                       supabase/{server, admin, database.types}, format
  hooks/               hooks shared by two or more screens
  proxy.ts             refreshes the session; not an authorization layer
supabase/migrations/   every schema change, RLS included
```

## Dependency direction

`app → screens → components → lib`. Screens and components use `data` (queries from Server Components, actions from Client Components). `data → lib`. `lib` imports only `lib`.

Never: a component importing a screen; `lib` importing `data` or `screens`; a Client Component importing `queries.ts` (`server-only` breaks the build if it happens).

## Data doors

| Need | Door | Where |
|---|---|---|
| Read data for a screen | Server Component calls a query | `data/<domain>/queries.ts` |
| Write from our own UI | Server Action from `authActionClient` + input schema | `data/<domain>/actions.ts` |
| External caller: webhook, cron, another system, file download | route handler wrapped by `route.user`, `route.webhook`, `route.cron` or `route.public` | `app/api/**/route.ts` |
| Work without a user session (webhook, cron) | admin client, ownership checked in code | `data/<domain>/admin.ts` or the route itself |

- Our screens never call our own `/api`. Server: call the query. Client: call the action.
- Actions and route handlers are thin adapters: session, schema, one call, response. Business rules live in functions in `data/<domain>/`. When a second caller needs the same logic, move it into such a function in the same change.
- `publicActionClient` and `route.public` are exceptions listed in every review. Each needs a reason (public contact form, health check) and rate limiting when it costs money, sends messages or writes data.
- Serverless functions have a time limit. Jobs that take minutes (bulk reminders, large imports) need a queue or a worker on the VPS, never a route. Realtime goes through Supabase Realtime, never WebSockets in Next. A separate backend only with a concrete reason, decided by the lead.

## Placement and names

- Colocate first. A piece used by one screen lives in that screen's folder. On the second consumer, move it to `components/<Feature>/` (UI) or `data/<domain>/` (logic) in the same change, and delete the old copy.
- Search before creating: look in `components/`, `hooks/`, `lib/` and `data/` for something that already does it.
- Files: `PascalCase.tsx` for components, `camelCase.ts` otherwise, `*.hook.ts` for hooks. Screen folders in PascalCase; domain folders in lowercase plural (`customers`), named from the glossary.
- Named exports only. Default exports only in `src/app` (Next requires them).
- Imports through `@/`, never `../../`. No barrel files (`index.ts` re-exporting): they drag server code into client bundles.
- Effects (`useEffect`, `useLayoutEffect`) only in `*.hook.ts` files or `src/hooks/`.
- Colors, spacing and radii through Tailwind tokens (`bg-primary`, `text-muted-foreground`), never hex.

## Recipes

### New screen
1. `src/screens/<Name>/<Name>Screen.tsx`, a Server Component by default.
2. `src/app/<route>/page.tsx` contains only `export default <Name>Screen;`.
3. Data comes from a query. If it needs a signed-in user, the query calls `requireUser()`.

### New read
`queries.ts` starts with `import 'server-only'`. Return types derive from `database.types` (`Pick<Row, …>`). Filter by owner even with RLS (states intent, uses the index). Throw the Supabase error (it extends `Error`). See `example/src/data/customers/queries.ts`.

### New write
1. Schema in `data/<domain>/schema.ts` with `v`; export `Input<>` (form) and `Output<>` (server) types from it.
2. Action: `authActionClient.inputSchema(schema).action(async ({ parsedInput, ctx }) => …)`. The owner is `ctx.user.id`, never an id sent by the client.
3. Form: Client Component with `useForm` + `zodResolver(schema)` + `useAction(action)`; show field errors and `result.serverError`.
4. Revalidate the affected path.
5. Messages meant for the user: `throw new ActionError('texto em português')`. Anything else reaches the user as a generic message.

### New route handler
1. `src/app/api/<name>/route.ts`: `export const POST = route.<mode>(async ({ request, params }) => …)`.
2. `params` and bodies arrive as `unknown`: parse them with a schema before use.
3. Webhook: `route.webhook(hmacSha256Verifier({ secret: env.X, header: '…', prefix: '…' }), handler)` or the provider SDK's check. The handler gets the verified raw `body`: `JSON.parse` it into `unknown`, then parse with a schema. Providers retry: store the event id and ignore repeats.
4. Cron: `route.cron(handler)`; the scheduler sends `Authorization: Bearer <CRON_SECRET>`.
5. Admin client only here or in `data/<domain>/admin.ts`, with an explicit owner filter in every query.

### New environment variable
Add it to `src/lib/env.ts` (server or client section, with a schema) and to `.env.example` with a comment. Secrets never get `NEXT_PUBLIC_`. Ask the user for the value; never invent one.

### New table
Migration `supabase/migrations/<timestamp>_<name>.sql`: create the table, index the owner column, enable RLS, one policy per operation with `(select auth.uid())`. Views with `security_invoker = true`. Regenerate `database.types.ts` (command in `supabase.md`). The lead applies migrations to production.

## Checklist

- [ ] Every `page.tsx` only renders a screen.
- [ ] No call to our own `/api` from our code.
- [ ] Every Server Action comes from `authActionClient`/`publicActionClient` with `inputSchema`.
- [ ] Every route handler is wrapped by `route.*`; the admin client appears only where allowed.
- [ ] Data from outside is parsed from `unknown`.
- [ ] Nothing used by two screens lives inside one screen's folder; no duplicated function.
- [ ] Effects only in hook files; tokens instead of hex.
- [ ] New tables have RLS and policies; `database.types.ts` regenerated.

## Do not replicate

- A `'use server'` file exporting plain async functions.
- A route handler without `route.*` because "it's internal".
- A screen fetching `/api/…` from its own app.
- `process.env` outside `lib/env.ts`; `NEXT_PUBLIC_` on a secret.
- Types written by hand for rows that `database.types` already describes.
- A `utils` file collecting unrelated helpers.
